# Wiremock Utilities

## Overview

This code defines a **TypeScript class named `WireMockClient` designed to programmatically interact with a running WireMock server's Admin API.** It provides utility methods to register new HTTP mock stubs, clear active configurations, verify if a specific request was received by the mock server, and bulk-upload JSON mock files from a local directory.

### 🧱 Core Architecture & Breakdown

The class interacts primarily with WireMock's default control endpoints via native `fetch` requests. Here is what each specific block does:

- **`constructor`**: Establishes the connection string. It strips any trailing slashes from the base URL and appends the standard WireMock control suffix `/__admin`.
- **`registerStub`**: Submits a POST request to `/mappings` to register a single mock endpoint definition. If the server responds with an error status, it intercepts it and throws an explicit description error.
- **`clearDynamicMocks`**: Resets the API stub state back to defaults by hitting the `/mappings/reset` endpoint.
- **`verifyRequestEmitted`**: Queries the `/requests/count` endpoint to verify if an outgoing system-under-test hit a specific route pattern during a test assertion loop.
- **`uploadDirectory`**: A bootstrapper helper that synchronously reads files out of a specified local directory, parses JSON configurations (supporting both arrays of stubs or standalone definitions), and pushes them up via sequential API registration calls.

### 📥 Expected Inputs

The class expects several inputs across its instantiation and respective methods.

#### Configuration / Class Instantiation

- **`baseUrl`** *(Optional String)*: The endpoint location of your active WireMock instance. If not provided, it falls back to the `MOCK_PROXY_URL` environment variable, or defaults cleanly to `'http://localhost:8080'`.

#### Method-Level Inputs

- **`registerStub(stub)`**:
  - `stub` *(Any / Object)*: A standard WireMock mapping schema object defining the request matching criteria and the mocked response payload.
- **`verifyRequestEmitted(method, urlPattern)`**:
  - `method` *(String)*: The HTTP verb to check (e.g., `'GET'`, `'POST'`).
  - `urlPattern` *(String)*: A WireMock-compatible URI string or regular expression to look up in the server logs.
- **`uploadDirectory(directoryPath)`**:
  - `directoryPath` *(String)*: A valid absolute or relative system path pointing to a directory that holds your `.json` mock declaration files.

### 📤 Emitted Outputs

The methods produce the following return signatures and structural side effects:

#### Return Signatures

- **`registerStub`**: Returns a **`Promise<string>`** resolving to the specific, unique identifier UUID generated by WireMock for that mapping definition.
- **`clearDynamicMocks`**: Returns a **`Promise<void>`** that resolves successfully once the mock layout is completely wiped.
- **`verifyRequestEmitted`**: Returns a **`Promise<boolean>`** resolving to `true` if the server logged at least 1 incoming request matching the criteria, otherwise `false`.
- **`uploadDirectory`**: Returns a **`Promise<void>`**. It doesn't yield data directly, but outputs diagnostic tracking messages using `console.info` or `console.error` logs to indicate file parsing states.

#### Network Side Effects

Modifies the active state of your running WireMock server instance over the network, dynamically adding or modifying mocking planes during local workbench tasks or test lifecycle hooks.

## Mock Files

This directory structure follows the standard conventions of a **WireMock standalone server** combined with your own custom workflow configurations. Together, these files simulate a fully functioning **Datadog API** workspace for your local development environment.

Here is a summary of what files in each directory do and the respective data schemas they follow.

### **`mappings/`**

**What it does:** Files here serve as the **routing and matching engine** for your mock server. They tell WireMock exactly which incoming HTTP request patterns to intercept (`request`) and how to construct the corresponding HTTP response stub (`response`).

**Schema Followed:** This folder strictly follows the official **WireMock Stub Mapping JSON Schema**.
  - `request`: Supports matching strategies like absolute paths (`url`), prefix paths (`urlPath`), query parameters, and custom request bodies.
  - `response`: Defines status codes, custom headers, and can either return an inline response body (`body`) or redirect the data layer to load external assets via `bodyFileName`.

### **`__files/`**

**What it does:** This folder acts as the **static asset storage** for large or complex response bodies. By keeping hefty data matrices out of your mapping definitions, your routing rules remain clean, readable, and easy to maintain.

**Schema Followed:** The folder follows **no single WireMock schema**; instead, each file adheres to the **exact upstream schema of the third-party provider API** you are mimicking.

In this instance, `datadog-monitors.json` mirrors the official structure of the **Datadog Monitors API GET Response** (`/api/v1/monitor`). It mimics standard Datadog telemetry entities such as alert definitions, query definitions, tags, and operational states (`Alert`, `Warn`, `OK`).

### **`vendor/`**

**What it does:** This is a **custom organization folder** you created for your workspace. WireMock does not native-load a `vendor` directory. It is used here to stage reference snapshots, raw seed data, or blueprints of external payloads (like your custom Datadog gauge metric streams) before they are dynamically registered by scripts like your `WireMockClient`.

**Schema Followed:** Like the `__files` directory, these assets track the **official vendor schema**—specifically the **Datadog Metrics Series Schema** (`/api/v1/series`). It tracks structural nodes like timestamped metric data points arrays and `gauge` types.
